How I work now

I write the spec: what a service owns, what it exposes, what it must never do, and the acceptance criteria. A coding agent does the implementation. I keep four things for myself: the architecture and the boundaries between services, anything touching tenant isolation or egress, the data model, and the acceptance criteria. Those are the decisions a client's security review asks about, and "the agent chose it" is not an answer. I read code when an eval fails or when the agent has over-engineered something, which is often.

The lesson I keep relearning: write the eval gold set, the real inputs and expected outputs, before the build. Acceptance criteria written in prose are ambiguous in ways the examples expose on day one.

Why code, not configuration

For a decade the answer to "automate this" was a workflow product: drag the boxes, wire the steps, hope the vendor's connector does what you need. That made sense when writing code was the expensive part. It isn't any more. A coding agent working from a clear spec produces a workflow as plain code faster than I can configure the same thing in a visual builder, and the result is better in every way that matters afterward. It is in version control. It diffs. It has tests. You can trace exactly what ran and why. Nobody is locked into a canvas.

That is the bet behind the pod platform. Each client's workflow is a code version of their process, written by an agent from a spec, running on shared headless services for identity, gateway, egress, monitoring and evals. Standing one up is fast, changing it is a conversation and a passing eval, and the client keeps the workflow code.

Where I think this is going

The interface is moving into the AI client. People will run, check on and change their automations from Claude, ChatGPT or whatever they already work in, so everything I build now is MCP-enabled from day one. Products built around a canvas are competing with a spec and a coding agent, and I think the spec wins. The work that stays human is deciding what to build, what the system must never do, and how you will know it worked. That is the job I want.

Pod platform

SectorFlow, September to October 2026

The services every pod runs on

Every managed agent we had shipped shared the same plumbing, hand-built each time: tenant identity, an API gateway, outbound egress controls, a control plane, an SDK. I needed it built once, deployed, and solid enough to onboard a paying client, with no other engineers free.

I split it into eight repositories and wrote a spec for each. Claude Code did the implementation, run as a tiered setup: one model planning and orchestrating across repos, a stronger one on the gateway and tenant isolation, a cheaper one on scaffolding, tests and docs.

A failed product

SectorFlow, 2025

Bidstra: six weeks to a prototype, then shut down

An agentic RFP-response tool: LangGraph multi-step reasoning over a retrieval layer of the company's past bids. Idea to working prototype in six weeks, then tested in buyer meetings. Buyers would not rely on AI-written responses for million-dollar bids. We stopped there rather than build further.

Why it's here: killing a prototype on evidence is part of the job. AI makes building cheap enough that the discipline is in deciding what not to build.
